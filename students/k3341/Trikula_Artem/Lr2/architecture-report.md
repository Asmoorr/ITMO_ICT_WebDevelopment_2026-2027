# Практики разработки современного Django-приложения для ЛР2

Дата исследования: **15 октября 2026 года**. Предмет: вариант 5 — сайт научных конференций; практики 2.1–2.3 — приложение об автовладельцах. Цель — выбрать архитектуру, достаточную для максимального балла и понятную при защите.

## 1. Основания и границы рекомендаций

Основные источники — документация разработчиков Django, PostgreSQL и Poetry; для контроля доступа — OWASP. Это первичные источники, описывающие поведение инструментов и проверяемые требования. Статьи с произвольной «идеальной архитектурой Django» не используются как нормативные требования.

Ниже разделены факты из документации и **проектные решения для нашей лабораторной**. Django не предписывает обязательные `services.py`, `selectors.py`, определённое число приложений или микросервисы. Предлагаемая структура — инженерный выбор под масштаб задания.

Сопоставление выполнено с [заданием ЛР2](https://rendex85.github.io/ITMO_ICT_WebDevelopment_Docs/lab2/assignment/), [практикой 2.1](https://rendex85.github.io/ITMO_ICT_WebDevelopment_Docs/lab2/practice1/), [практикой 2.2](https://rendex85.github.io/ITMO_ICT_WebDevelopment_Docs/lab2/practice2/), [практикой 2.3](https://rendex85.github.io/ITMO_ICT_WebDevelopment_Docs/lab2/practice3/) и [правилами отчётов](https://rendex85.github.io/ITMO_ICT_WebDevelopment_Docs/submission/mkdocs-deploy/). Предложения о сроках заявок и отзывов — принятые нами правила, а не дополнительные требования методички.

## 2. Версии и воспроизводимость

На дату исследования последняя официальная стабильная версия — **Django 6.1.2**, выпущенная 6 октября 2026 года. Это обычный стабильный релиз, не alpha, beta, RC или ветка разработки. Ветка 5.2 LTS тоже поддерживается, но не является последней стабильной; согласно решению пользователя выбираем 6.1.2. Перед установкой следует ещё раз проверить актуальный patch-релиз. Источники: [загрузка Django](https://www.djangoproject.com/download/), [примечания к 6.1.2](https://docs.djangoproject.com/en/6.1/releases/6.1.2/).

Django 6.1 поддерживает Python 3.12–3.14. В существующем окружении обнаружен Python 3.13.14. Django поддерживает PostgreSQL начиная с 15; установленный PostgreSQL 17 подходит. Для подключения выбираем современный драйвер **psycopg 3**, рекомендованный документацией. Источники: [совместимость Python](https://docs.djangoproject.com/en/6.1/releases/6.1/#python-compatibility), [PostgreSQL backend](https://docs.djangoproject.com/en/6.1/ref/databases/#postgresql-notes).

**Решение:** сохранить существующее окружение Poetry, обновить ограничение Python в `pyproject.toml` под выбранные зависимости, фиксировать разрешённые версии в `poetry.lock` и включать lock-файл в Git. Установку на другом компьютере выполнять из lock-файла; `.venv` не переносить. Общие зависимости практик и основного варианта допустимы, пока требования совместимы. [Poetry: базовое использование и lock-файл](https://python-poetry.org/docs/basic-usage/).

## 3. Общая архитектура

**Рекомендуется модульное серверное приложение:** Django формирует HTML, PostgreSQL хранит данные, браузер отправляет обычные GET/POST-запросы. Для текущих сценариев достаточно синхронных views. Отдельный API, SPA, Redis, очередь задач и микросервисы сейчас не нужны. Это решение по масштабу, а не ограничение Django.

Основа — слабая связанность частей, отсутствие повторяющихся правил и явные зависимости. Модели содержат сведения и поведение предметных объектов; шаблоны отвечают за представление данных. [Философия Django](https://docs.djangoproject.com/en/6.1/misc/design-philosophies/).

Разделение ответственности:

| Часть | Что размещаем | Пример для ЛР2 |
|---|---|---|
| URLconf | Именованные маршруты и пространства имён | `conferences:detail` |
| View | HTTP, проверка доступа, вызов формы/операции, ответ | Обработчик подачи заявки |
| Form / ModelForm | Допустимые поля, разбор и ошибки ввода | Название и аннотация доклада |
| Model | Связи, ограничения, локальная логика объекта | Период конференции, статус заявки |
| QuerySet | Повторяемые выборки | Конференции по теме, заявки пользователя |
| Прикладная операция | Сценарий из нескольких проверок/записей | Изменение результата выступления |
| Template | Разметка, ссылки, отображение ошибок | Каталог и личные заявки |

Для многосоставных действий допустим `services.py` с обычными функциями, например `submit_registration()` или `set_publication_result()`. Простое сохранение справочника не требует отдельного сервиса. Не нужно оборачивать каждый ORM-запрос в repository-класс. Операции должны переиспользоваться сайтом и Admin, когда реализуют один и тот же сценарий.

Основной путь изменения данных делаем явным. Не размещаем подачу заявки, изменение результата или проверку прав в цепочках сигналов: документация предупреждает, что неявные вызовы усложняют отладку и внутри одного проекта часто лучше прямой вызов функции. [Django: сигналы](https://docs.djangoproject.com/en/6.1/topics/signals/#defining-and-sending-signals).

## 4. Организация проектов

После выполнения практик структура уточнена: практики 2.1–2.3 представляют этапы развития одного приложения и объединены, чтобы не дублировать модели, формы, шаблоны и проверки.

```text
Lr2/
    practical_works/          # единый проект автовладельцев
        manage.py
        django_project_trikula/
        project_first_app/
    variant5/                # отдельный проект конференций
        manage.py
        config/
        accounts/
        conferences/
    .env
    .env.example
```

Внутри `variant5` приложения `accounts` и `conferences` относятся к одному серверу. Заявки и отзывы остаются рядом с конференциями, пока их ответственность не требует выделения.

Практики используют одну базу `lr2_practices`, один набор миграций и одну расширенную модель пользователя с самого начала. Отчёт сохраняет три страницы по заданиям. Конференции используют отдельную `lr2_conferences`: разные проекты нельзя мигрировать в общую базу с совпадающими именами таблиц.

## 5. Модель данных конференций

Предлагаемый состав:

| Модель | Назначение и важные поля |
|---|---|
| `User` | Стандартная учётная запись, ФИО; при необходимости организация |
| `Topic` | Тематика конференции |
| `Venue` | Название, адрес и описание места проведения |
| `Conference` | Название, описание, начало/окончание, условия участия, место, тематики |
| `Registration` | Автор, конференция, название/аннотация доклада, результат, время создания/изменения |
| `Review` | Автор, конференция, текст, рейтинг, даты конференции, время публикации |

`Conference` связан с тематиками как M2M, с местом как FK. `Registration` — самостоятельная сущность связи пользователя и конференции с собственными атрибутами; при необходимости M2M можно объявить через `through`. Выбор связей и имён основан на [документации моделей](https://docs.djangoproject.com/en/6.1/topics/db/models/).

Для первой версии предлагаем одну заявку пользователя на конференцию и один отзыв пользователя на конференцию. Это наши правила, не универсальная модель научных мероприятий. Если нужны несколько докладов одного автора или соавторство, схему нужно изменить до реализации.

Результат выступления храним через `TextChoices`: «не рассмотрен», «рекомендован», «не рекомендован». Boolean не передаёт состояние ожидания. Отмена регистрации может быть удалением записи, как допускает задание; не смешиваем её с результатом публикации.

Даты конференции в отзыве сохраняем как снимок периода на момент публикации: это позволяет буквально выполнить требование задания и не менять историю отзыва при редактировании конференции. Их назначает сервер; пользователь не вводит произвольный период. Редактирование текста отзыва не должно пересоздавать снимок. Это сознательное исключение из нормализации ради исторического смысла данных.

Политику `on_delete` выбираем по смыслу: например, `PROTECT` для места, используемого конференциями; для удаления самой конференции явно решаем судьбу заявок и отзывов. Не ставим `CASCADE` повсюду автоматически. Паспорт и адрес из практики об автовладельцах в сайт конференций не переносим: у него другая предметная область.

## 6. Целостность и проверка данных

Ошибки ввода показываем через формы, но долговременные инварианты закрепляем в БД:

- `UniqueConstraint` для пары автор–конференция в заявках и отзывах;
- `CheckConstraint` для рейтинга 1–10;
- `CheckConstraint` для окончания конференции не раньше начала;
- при необходимости ограничение множества допустимых статусов: `choices` само по себе не заменяет SQL-ограничение.

Источники: [ограничения Django](https://docs.djangoproject.com/en/6.1/ref/models/constraints/), [ограничения PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-constraints.html).

Проверки «конференция уже закончилась», «автор участвовал» и «заявку ещё разрешено менять» зависят от времени и других записей. Их выполняет прикладная операция. PostgreSQL не рекомендует выражать межстрочные проверки через `CHECK`; изменение времени также не запускает повторную проверку сохранённых строк.

Нельзя считать, что `save()` проверит модель: `full_clean()` автоматически не вызывается. `ModelForm.is_valid()` выполняет модельную валидацию для включённых полей; исключённые поля требуют отдельного внимания. Записи из команд наполнения и прикладных операций тоже должны проходить нужные проверки. [Валидация экземпляров](https://docs.djangoproject.com/en/6.1/ref/models/instances/#validating-objects).

## 7. Транзакции и одновременные изменения

Операции из нескольких связанных записей выполняем в коротком `transaction.atomic()`. `IntegrityError` обрабатываем вокруг блока, после отката. Внешние действия, если они появятся, запускаем через `on_commit()`; отправка письма не должна происходить до успешного сохранения заявки. Оборачивать каждый запрос сайта в транзакцию через `ATOMIC_REQUESTS` без необходимости не предлагаем. [Транзакции Django](https://docs.djangoproject.com/en/6.1/topics/db/transactions/).

Предварительное `.exists()` не защищает от двух одновременных заявок: окончательную гарантию даёт уникальное ограничение. Если понадобится согласовать проверку срока с одновременным редактированием конференции, используем `select_for_update()` внутри транзакции и единый порядок блокировок во всех конкурирующих операциях. Одна блокировка без общей дисциплины записи проблему не решает. Проверки блокировок выполняем на PostgreSQL с `TransactionTestCase`. [QuerySet: блокировки](https://docs.djangoproject.com/en/6.1/ref/models/querysets/#select-for-update).

## 8. Пользователи, роли и доступ

Сразу создаём `accounts.User(AbstractUser)` и задаём `AUTH_USER_MODEL` до первой миграции. Связи с пользователем объявляем через `settings.AUTH_USER_MODEL`. В практиках дополнительные поля пользователя — паспорт, адрес и национальность; в основном варианте добавляем только нужные конференциям сведения. [Настройка модели пользователя](https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#substituting-a-custom-user-model).

Для браузерного сайта используем встроенную аутентификацию и сессии Django, стандартные механизмы хеширования и формы регистрации. JWT и собственное хранение паролей здесь не требуются. Пароль создаём через корректную пользовательскую форму/`create_user()`, а не присваиванием открытой строки в поле `password`. [Аутентификация Django](https://docs.djangoproject.com/en/6.1/topics/auth/default/).

Матрица доступа для проекта:

| Действие | Гость | Пользователь | Организатор с правами |
|---|---|---|---|
| Каталог, карточки и публичные отзывы | Да | Да | Да |
| Подать заявку | Нет | От своего имени | От своего имени |
| Изменить/удалить заявку до начала | Нет | Только свою | Управление по отдельному разрешению |
| Написать отзыв после окончания | Нет | При наличии участия | По тем же правилам участия |
| Изменить результат выступления | Нет | Нет | Да |
| Таблица участников | Нет | По принятой политике видимости | Да |

В таблице участников рекомендуем показывать ФИО, доклад и результат, а контактные данные — только организатору. Страницы таблицы реализуем обязательно; политика видимости — проектное решение.

Скрытая кнопка не является защитой. Каждый POST и получение защищённого объекта проверяются сервером. Для личных записей ограничиваем queryset текущим пользователем; автора берём из `request.user`. Права проверяем по принципу минимальных привилегий, включая прямой запрос к чужому ID. [OWASP: Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

`is_staff` даёт признак допуска к Admin, но сам по себе не выдаёт все предметные полномочия. Для организаторов предлагаем группу и разрешения Django, включая отдельное право изменения результата. Проверка владения объектом остаётся явной: стандартный backend Django не реализует объектные права автоматически. Проверку видимости кнопок строим на той же политике, что серверный обработчик. [Права на объекты и custom permissions](https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#handling-object-permissions).

## 9. Формы, views и шаблоны

В `ModelForm` явно перечисляем разрешённые поля. Пользовательские формы не принимают автора, `is_staff`, `is_superuser` или результат выступления. Отдельная административная форма принимает только разрешённые организатору изменения. Это предотвращает незаметное расширение доступа после добавления поля модели. [Безопасный выбор полей ModelForm](https://docs.djangoproject.com/en/6.1/topics/forms/modelforms/#selecting-the-fields-to-use).

FBV и CBV одинаково допустимы. Для типовых списков/карточек удобны generic views; отдельное действие вроде смены результата может быть проще как FBV. В практиках обязательно сохраняем требуемое распределение: владельцы через FBV, автомобили через CBV. Не строим глубокие цепочки миксинов ради формального использования классов. [Введение в CBV](https://docs.djangoproject.com/en/6.1/topics/class-based-views/intro/).

Для основного сайта подключаем backend Jinja2; `DjangoTemplates` сохраняем для Admin и стандартных компонентов. Используем разные каталоги (`jinja2/` и `templates/`) и при необходимости явный выбор движка. В окружение Jinja2 добавляем `url`/`static`; используем `{{ csrf_input }}` и вызовы методов со скобками. Синтаксис тегов Django не переносится автоматически. [Django: шаблоны и Jinja2](https://docs.djangoproject.com/en/6.1/topics/templates/#django.template.backends.jinja2.Jinja2).

Общие элементы выносим в базовый шаблон. Шаблон получает подготовленные данные и признаки доступных действий; не выполняет сложные выборки и изменение БД. После успешного POST делаем redirect, чтобы обновление страницы не повторяло отправку. Именованные URL позволяют менять маршруты без исправления строк по всему проекту.

Все изменения выполняются POST-запросами с CSRF-защитой; GET остаётся чтением, включая страницу подтверждения удаления. Не отключаем CSRF ради удобства. [CSRF в Django](https://docs.djangoproject.com/en/6.1/howto/csrf/).

Оставляем автоматическое HTML-экранирование и не применяем `safe` к пользовательским отзывам. ORM используем с параметрами, без сборки SQL из пользовательских строк. Ограничиваем допустимые поля сортировки. [Безопасность Django](https://docs.djangoproject.com/en/6.1/topics/security/).

## 10. Поиск, пагинация и производительность

Последовательность каталога: проверка GET-параметров → фильтрация queryset → устранение дублей при M2M-поиске → стабильная сортировка → пагинация → рендер. Предлагаемые фильтры: тематика, место, период и состояние конференции; поиск — название и описание. Это покрывает требования максимального балла без внешнего поискового сервиса.

Используем `Paginator` или `paginate_by`. У сортировки должен быть однозначный дополнительный ключ, например `start_date, pk`; при переходе между страницами сохраняем поисковые параметры. Для некорректных параметров показываем понятную ошибку либо документированное безопасное значение. [Пагинация Django](https://docs.djangoproject.com/en/6.1/topics/pagination/).

Для FK применяем `select_related()`, для M2M и обратных связей — `prefetch_related()`, когда связанные данные действительно нужны. Число участников и средний рейтинг можно получать агрегацией; несколько JOIN способны исказить агрегаты, поэтому проверяем результат на характерных данных. Не добавляем индексы вслепую: сначала анализ запросов. Обычный B-tree не следует считать универсальным ускорителем `icontains`. Полнотекстовый поиск и кэширование оставляем до появления измеренной необходимости. [Оптимизация ORM](https://docs.djangoproject.com/en/6.1/topics/db/optimization/).

## 11. Admin, настройки и запуск

В Admin настраиваем списки, поиск, фильтры, readonly-поля и ограничения редактирования. Возможность выставления результата выступления сохраняем в Admin, как требует вариант; также делаем её на отдельной странице сайта. Admin предназначен прежде всего для внутреннего управления, а пользовательские процессы разумно реализовывать собственными views. [Назначение Admin](https://docs.djangoproject.com/en/6.1/ref/contrib/admin/).

Настройки подключения и `SECRET_KEY` читаем из окружения; `.env` — локальный способ загрузки этих значений, не встроенная гарантия Django. Используем абсолютный путь к согласованному `Lr2/.env`, чтобы запуск не зависел от текущего каталога. В Git включаем только `.env.example`. При отсутствии обязательных значений завершаем запуск понятной ошибкой вместо подключения к случайной БД.

Созданные `lr2_user` и `lr2_conferences` используем для основного варианта. Пароль `pass` соответствует согласованной локальной конфигурации; он не переносится в публичное окружение. Приложение работает под отдельной ролью БД без superuser. Для тестовой БД заранее определяем отдельную роль или подготовленную базу, а не включаем `CREATEDB` приложению без необходимости.

Разделяем локальные и публикационные настройки: в публичном окружении `DEBUG=False`, корректный `ALLOWED_HOSTS`, HTTPS и secure cookies. Перед публикацией запускаем `check --deploy`. Не используем `runserver` как публичный сервер. [Checklist развёртывания](https://docs.djangoproject.com/en/6.1/howto/deployment/checklist/).

Синхронные views — достаточный выбор для CRUD. ASGI/async добавляются при конкретной потребности; асинхронность не делает обычные формы автоматически быстрее и требует учитывать ограничения транзакций. [Асинхронная поддержка](https://docs.djangoproject.com/en/6.1/topics/async/).

GitHub Pages публикует только MkDocs-отчёт, а не Python-приложение с PostgreSQL. Для защиты достаточно отдельно описанного локального запуска сайта; публичный backend-хостинг — самостоятельная задача.

## 12. Проверки и документация

Нужны тесты поведения, которое легко сломать и трудно проверить одной демонстрацией:

1. Регистрация, вход и выход; пользователь не может назначить себе привилегии.
2. Чужие заявки и отзывы нельзя изменить прямым запросом, в том числе с подменой ID.
3. Заявка редактируется до начала конференции; граничное время проверяется отдельно.
4. Повторная заявка и повторный отзыв запрещены ограничениями БД.
5. Отзыв доступен участнику после окончания; рейтинг ограничен 1–10.
6. Результат меняется только уполномоченным пользователем и одинаково валидируется через сайт и Admin.
7. Поиск, фильтры и пагинация работают совместно и не дублируют конференции.
8. Пользовательский текст экранируется; CSRF проверяется клиентом с `enforce_csrf_checks=True`.

Тестируем на PostgreSQL, чтобы не скрыть различия ограничений и транзакций за SQLite. Стандартный Django test runner создаёт отдельную тестовую БД, поэтому заранее проверяем полномочия тестовой роли и имя базы. Для транзакционных сценариев используем подходящий класс теста. [Тестирование Django](https://docs.djangoproject.com/en/6.1/topics/testing/overview/).

Миграции сохраняем в Git вместе с изменениями моделей. Данные для демонстрации загружаем повторяемой management-командой с вымышленными участниками. Не удаляем миграции ради устранения каждого конфликта; фиксируем реальные изменения схемы. [Миграции Django](https://docs.djangoproject.com/en/6.1/topics/migrations/).

В README описываем установку Poetry-зависимостей, настройку БД и `.env`, применение миграций, наполнение, запуск и тесты. В MkDocs — модель данных, матрицу прав, реализованные страницы, основные views/формы/шаблоны и реальные скриншоты. Планируемые возможности не выдаём за уже выполненные.

## 14. Противоречия, неточности и отличия от методички

### 14.1. Версия Django: прямое расхождение с перечнем ПО

Задание перечисляет Python 3.6+ и Django 3. Ветки Django 3 уже не поддерживаются; официальная страница рекомендует актуальные patch-релизы поддерживаемых веток. Django 6.1 требует Python минимум 3.12. Следовательно, диапазон «3.6+» нельзя воспринимать как совместимость любого такого Python с выбранным Django. Используем 6.1.2 и Python 3.13 по решению пользователя; в отчёте явно указываем версии. [Версии и поддержка](https://www.djangoproject.com/download/), [совместимость 6.1](https://docs.djangoproject.com/en/6.1/releases/6.1/#python-compatibility).

### 14.2. Jinja2 и шаблонный язык Django: несогласованность учебных материалов

ЛР требует Jinja2, тогда как практики показывают `{% url %}`, `{% csrf_token %}`, `{% empty %}` и Django-фильтры. Это разные языки; похожий синтаксис не делает их взаимозаменяемыми. Решение: практики можно воспроизвести с DjangoTemplates; основной сайт — Jinja2, Admin — DjangoTemplates. В Jinja2 применяем документированные `csrf_input` и функции `url`/`static`. Это не противоречие современной практике: оба backend официально поддерживаются. [Шаблонные backend](https://docs.djangoproject.com/en/6.1/topics/templates/).

### 14.3. Запрет `.add()` с промежуточной моделью: фактическая неточность

В практике 2.2 сказано, что добавление через `.add()` невозможно при явной промежуточной модели. Современная документация описывает `.add(..., through_defaults={...})`, позволяющий передать её дополнительные поля. Однако операция не вызывает `save()` промежуточных экземпляров. Для наших заявок явное создание `Registration` в прикладной операции всё равно понятнее: у неё самостоятельный жизненный цикл и проверки. [RelatedManager.add](https://docs.djangoproject.com/en/6.1/ref/models/relations/#django.db.models.fields.related.RelatedManager.add).

### 14.4. `get_user_model()` при импорте: слишком категоричное утверждение

Практика 2.3 утверждает, что вызов на уровне модуля вне функций небезопасен и возможен только после полной загрузки приложений. Официальная документация допускает `get_user_model()` во время импорта моделей. Конкретные проблемы возможны при неправильном порядке инициализации или кэшировании модели в тестах с её заменой, но общий запрет неверен. Для внешних ключей всё равно выбираем `settings.AUTH_USER_MODEL`. [Ссылки на модель пользователя](https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#referencing-the-user-model).

### 14.5. `is_staff` в шаблоне: необходимое дополнение, а не отмена требования

Методичка объясняет клиентское разграничение через `{% if user.is_staff %}`. Это управление отображением, а не серверная авторизация. Дополняем его проверкой разрешений и владения объектом на каждом защищённом запросе. Сам признак staff не трактуем как все права организатора. [OWASP: проверка доступа](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [Admin и staff](https://docs.djangoproject.com/en/6.1/ref/contrib/admin/).

### 14.6. Порядок изменения пользователя и учебные упрощения

Практики сначала работают с владельцем, затем превращают его в пользователя. Для нового рабочего проекта модель пользователя следует определить заранее, чтобы избежать сложной замены после миграций. Учебные этапы объединены в один проект с `AbstractUser` до первой миграции; основной вариант также начинаем с `AbstractUser`. [Custom User с начала проекта](https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project).

SQLite в примерах, абсолютные URL в строках и минимальные HTML-формы — упрощения обучения, а не основания отказаться от PostgreSQL, именованных маршрутов или CSS. MVC/MVT — различие терминологии, не конфликт архитектуры. Обязательное применение FBV/CBV в практиках совместимо с современным Django. Выставление результатов через Admin также сохраняем: требование клиентского интерфейса его дополняет.
